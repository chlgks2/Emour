## 1. 아키텍처 개요

### 1.1 구성

단일 EC2 인스턴스 위에 **호스트 Nginx(리버스 프록시) + Docker 컨테이너 8개** 구조.
운영(prod)과 개발(dev)을 **같은 서버에서 포트로 분리**해 동시 운영한다.

```
                    인터넷
                       │
        ┌──────────────┴──────────────┐
     :443 (prod)                  :8080 (dev)
        │                              │
        └──────── 호스트 Nginx 1.24.0 ─┘
                       │  (모든 프록시 대상은 127.0.0.1 로만 바인딩)
   ┌───────────┬───────┼────────┬─────────────┐
   │           │       │        │             │
 prod-web   prod-api  prod-ai  dev-web/api/ai  정적파일
 :8091      :8092     :8093    :8081/2/3      /opt/emour/data/uploads
   │           │        │
   └───────────┴────────┴──── Docker 네트워크 `emour-net` ────┐
                                                              │
                                                  emour-db(MySQL 8.0)
                                                  emour-redis(Redis 7)
                                                  ※ 두 컨테이너는 dev/prod 공용
```

### 1.2 URL 라우팅

| 경로 | prod(:443) 전달 대상 | dev(:8080) 전달 대상 | 설명 |
| --- | --- | --- | --- |
| / | 127.0.0.1:8091 | 127.0.0.1:8081 | React SPA |
| /api/ | 127.0.0.1:8092/ | 127.0.0.1:8082/ | Spring Boot REST API |
| /ws/ | 127.0.0.1:8092 | 127.0.0.1:8082 | WebSocket(STOMP) 채팅 |
| /ai/ | 127.0.0.1:8093/ | 127.0.0.1:8083/ | FastAPI 감정 분석 / 답장 추천 |
| /uploads/ | alias /opt/emour/data/uploads/ | 동일 | 업로드 이미지 정적 서빙 |

> **용어 보조설명 — 리버스 프록시(reverse proxy)**: 외부 요청을 대신 받아 내부 서버로 넘겨주는 중계 서버. 여기서는 Nginx가 443/8080 포트만 외부에 노출하고, 실제 애플리케이션 컨테이너는 전부 `127.0.0.1`(서버 자기 자신)에만 열려 있어 외부에서 직접 접근할 수 없다.
>

## 3. 서버 초기 세팅

### 3.1 필수 패키지 설치

```bash
# Docker Engine + Compose 플러그인
sudo apt-get update
sudo apt-get install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL <https://download.docker.com/linux/ubuntu/gpg> \
     -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc]\
<https://download.docker.com/linux/ubuntu$>(. /etc/os-release&&echo$VERSION_CODENAME) stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io \
     docker-buildx-plugin docker-compose-plugin

# 현재 사용자를 docker 그룹에 추가 (재로그인 필요)
sudo usermod -aG docker $USER

# Nginx, Certbot
sudo apt-get install -y nginx certbot python3-certbot-nginx
```

### 3.2 디렉토리 구조 및 권한

```bash
/opt/emour/                       drwxrwsr-x ubuntu:deploy
├── prod/
│   ├── docker-compose.yml
│   ├── .env                      (WEB_TAG / API_TAG / AI_TAG)
│   └── env/
│       ├── api.env               -rw-r----- ubuntu:deploy (640)
│       └── ai.env                -rw-r----- ubuntu:deploy (640)
├── dev/
│   ├── docker-compose.yml
│   ├── .env
│   └── env/
│       ├── api.env
│       └── ai.env
├── data/
│   ├── docker-compose.db.yml     (MySQL + Redis + emour-net 정의)
│   ├── db.env                    (MySQL 계정 정보)
│   ├── .env                      (REDIS_PASSWORD — compose 치환용)
│   ├── mysql/                    (MySQL 데이터 영구 볼륨)
│   ├── redis/                    (Redis 데이터 영구 볼륨)
│   ├── uploads/                  (업로드 이미지 — dev/prod 공용)
│   └── backup/                   (자동 백업 산출물)
└── scripts/
    ├── deploy.sh
    ├── backup.sh
    └── cleanup.sh
```

생성 명령:

```bash
sudo groupadd -f deploy
sudo usermod -aG deploy ubuntu

sudo mkdir -p /opt/emour/{prod/env,dev/env,data/{mysql,redis,uploads,backup},scripts}
sudo chown -R ubuntu:deploy /opt/emour
sudo chmod -R g+ws /opt/emour            # setgid: 하위 생성 파일이 deploy 그룹 상속
sudo chmod 640 /opt/emour/*/env/*.env    # env 파일은 소유자/그룹만 읽기
```

> **`g+s`(setgid 비트)**: 디렉토리에 걸면 그 안에서 새로 만들어지는 파일이 자동으로 상위 디렉토리와 같은 그룹(`deploy`)을 갖는다. CI Runner가 만든 파일과 `ubuntu` 계정이 만든 파일의 권한이 어긋나는 것을 막는다.
> 

### 3.3 방화벽(UFW)

```bash
sudo ufw allow 22/tcp     comment 'SSH'
sudo ufw allow 80/tcp     comment 'HTTP redirect + ACME'
sudo ufw allow 443        comment 'HTTPS prod'
sudo ufw allow 8080/tcp   comment 'dev entry'
sudo ufw enable
sudo ufw status verbose
```

현재 적용 상태 (2026-08-09 기준):

```bash
Default: deny (incoming), allow (outgoing), deny (routed)

22          ALLOW IN   Anywhere
22/tcp      ALLOW IN   Anywhere   # SSH
80/tcp      ALLOW IN   Anywhere   # HTTP redirect + ACME
443         ALLOW IN   Anywhere
8080/tcp    ALLOW IN   Anywhere   # dev entry
8989/tcp    ALLOW IN   Anywhere   # SSAFY 서버 기본 규칙(이전 기수 잔여) — 건드리지 않음
```

> AWS 콘솔의 EC2 보안 그룹에도 인바운드 `80/tcp`가 별도로 열려 있어야 한다. UFW는 OS 내부 방화벽, 보안 그룹은 그 앞단이라 둘 다 열려야 외부에서 도달한다.
> 

80은 8.3의 리다이렉트 블록 및 8.6의 Certbot webroot 인증에 사용된다. 과거 미개방 상태였던 이력은 10.2에 해결 완료 항목으로 기록.

### 3.4 Docker 네트워크

`emour-net`은 `data/docker-compose.db.yml`이 생성하고, `prod/`·`dev/` compose는 `external: true`로 **참조만** 한다. 따라서 **DB compose를 가장 먼저 기동해야 한다.**

```bash
cd /opt/emour/data
docker compose -f docker-compose.db.yml up -d
docker network ls | grep emour-net
```

### 6.4 이미지 빌드

CI가 수행하는 것과 동일한 명령이다. 수동 빌드 시 태그 규칙(`master-*` / `develop-*`)을 지켜야 `deploy.sh`가 거부하지 않는다.

```bash
# 프론트엔드 — VITE_* 는 반드시 --build-arg 로 넘긴다(빌드 시점에 코드에 박힘)
docker build \
  --build-arg VITE_API_BASE_URL=/api \
  --build-arg VITE_WS_BASE_URL=/ws \
  --build-arg VITE_GOOGLE_CLIENT_ID='<GOOGLE_CLIENT_ID>' \
  -t emour-web:master-999 ./frontend

# 백엔드
docker build -t emour-api:master-999 ./backend/Emour

# AI (모델 캐시 갱신 이슈 방지 위해 --no-cache)
docker build --no-cache -t emour-ai:master-999 ./AI
```

> **보조설명 — 왜 `VITE_*`는 `--build-arg`인가**: Vite는 `import.meta.env.VITE_*` 값을 **빌드 시점에 정적 문자열로 치환**한다. 컨테이너 실행 시 환경변수를 넣어봐야 이미 번들에 박힌 값은 바뀌지 않는다. 그래서 Dockerfile에 `ARG` → `ENV` 로 받아 `npm run build` 이전에 주입한다.
> 
> 
> `VITE_AI_BASE_URL`은 CI에서 넘기지 않으며 Dockerfile 기본값 `/ai`를 사용한다.
> 

### 6.5 배포

```bash
/opt/emour/scripts/deploy.sh <env> <service> <tag>
# env     : dev | prod
# service : web | api | ai
# tag     : dev는 develop-* , prod는 master-* 만 허용

# 예시
/opt/emour/scripts/deploy.sh prod api master-999
```

`deploy.sh` 동작 순서:

1. **태그 접두사 검증** — `prod`에 `develop-*`를 배포하려 하면 즉시 실패 (환경 교차 배포 방지)
2. `/opt/emour/<env>/.env` 의 `WEB_TAG|API_TAG|AI_TAG` 를 `sed`로 치환
3. `docker compose up -d <service>` — **해당 서비스만** 재기동
4. 헬스체크를 5초 간격 최대 40회(약 200초) 수행
    - `web` → `http://127.0.0.1:<BASE>1/`
    - `api` → `http://127.0.0.1:<BASE>2/actuator/health`
    - `ai` → `http://127.0.0.1:<BASE>3/health`
    - `BASE`는 prod=`809`, dev=`808`
5. 성공 시 `docker image prune -f`, 실패 시 최근 로그 100줄 출력 후 exit 1

### 6.6 수동 기동 / 중지

```bash
cd /opt/emour/prod           # 또는 /opt/emour/dev
docker compose up -d         # 전체 기동
docker compose ps
docker compose logs -f api   # 로그 추적
docker compose restart ai
docker compose down          # 전체 중지 (DB/Redis는 별도라 영향 없음)
```

`prod/docker-compose.yml`은 이미지 태그가 `${API_TAG:?...}` 형식이다. `:?`는 **변수가 없으면 에러로 중단**시키는 문법으로, `latest` 같은 의도치 않은 이미지가 운영에 뜨는 사고를 막는다. dev는 `${API_TAG:-latest}`를 쓴다.

## 8. Nginx 및 HTTPS

### 8.1 활성 사이트

```
/etc/nginx/sites-enabled/prod -> /etc/nginx/sites-available/prod
/etc/nginx/sites-enabled/dev  -> /etc/nginx/sites-available/dev
```

### 8.2 WebSocket 업그레이드 map (필수 선행 설정)

`/etc/nginx/conf.d/websocket.conf`:

```
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}
```

이 `map` 블록이 없으면 사이트 설정의 `proxy_set_header Connection $connection_upgrade;` 가 미정의 변수를 참조해 **Nginx가 기동하지 않는다.** 사이트 설정보다 먼저 배치해야 한다.

### 8.3 prod (`/etc/nginx/sites-available/prod`)

#### 8.3.1 HTTP(80) → HTTPS 리다이렉트 + ACME 챌린지

별도 사이트 파일 `/etc/nginx/sites-available/http-redirect`로 분리했다. `443` 서버 블록과 합치지 않은 이유는 인증서 갱신용 `/.well-known/acme-challenge/`가 TLS 없이 평문 80번으로 들어오기 때문이다.

```
server {
    listen80;
    server_namei15b208.p.ssafy.io;

    location /.well-known/acme-challenge/ {
        root/var/www/html;
    }
    location / {
        return 301 https://$host$request_uri;
    }
}
```

적용:

```bash
sudo mkdir -p /var/www/html
sudo ln -sf /etc/nginx/sites-available/http-redirect /etc/nginx/sites-enabled/http-redirect
sudo nginx -t && sudo systemctl reload nginx
```

검증:

```bash
curl -I -m 5 <http://i15b208.p.ssafy.io>
# HTTP/1.1 301 Moved Permanently
# Location: <https://i15b208.p.ssafy.io/>
```

#### 8.3.2 HTTPS(443) 본 서버 블록

```
server {
    listen443 ssl http2;
    server_namei15b208.p.ssafy.io;
    ssl_certificate    /etc/letsencrypt/live/i15b208.p.ssafy.io/fullchain.pem;
    ssl_certificate_key/etc/letsencrypt/live/i15b208.p.ssafy.io/privkey.pem;
    ssl_protocolsTLSv1.2 TLSv1.3;

    add_headerStrict-Transport-Security "max-age=31536000" always;
    add_headerX-Content-Type-Options "nosniff" always;

    client_max_body_size30m;

    location /ws/ {
        proxy_passhttp://127.0.0.1:8092;
        proxy_http_version1.1;
        proxy_set_headerUpgrade    $http_upgrade;
        proxy_set_headerConnection $connection_upgrade;
        proxy_set_headerHost       $host;
        proxy_read_timeout3600s;
    }
    location /api/ {
        proxy_passhttp://127.0.0.1:8092/;
        proxy_set_headerHost              $host;
        proxy_set_headerX-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_headerX-Forwarded-Proto $scheme;
    }
    location /ai/ {
        proxy_passhttp://127.0.0.1:8093/;
        proxy_read_timeout300s;
        proxy_bufferingoff;
    }
    location /uploads/ { alias/opt/emour/data/uploads/; }
    location / {
        proxy_passhttp://127.0.0.1:8091;
        proxy_set_headerHost $host;
    }
}
```

설정 의도:

- `client_max_body_size 30m` — 이미지 업로드 허용 크기
- `/ws/` `proxy_read_timeout 3600s` — 채팅 WebSocket 연결이 1시간 유휴 상태여도 끊기지 않도록
- `/ai/` `proxy_read_timeout 300s`, `proxy_buffering off` — 모델 추론이 오래 걸릴 수 있고, 응답을 버퍼링 없이 즉시 전달
- `/api/`와 `/ai/`의 `proxy_pass` 끝에 붙은 **`/`** 는 접두사(`/api`, `/ai`)를 떼고 전달하라는 의미다. 단 FastAPI는 `root_path="/ai"`로 떠 있어 문서(`/ai/docs`) 경로가 정상 동작한다.
- `/ws/`에는 끝 `/`가 **없다** — STOMP 엔드포인트 경로를 그대로 보존해야 한다.

### 8.4 dev (`/etc/nginx/sites-available/dev`)

prod와 동일 구조이며 차이만 정리한다.

| 항목 | prod | dev |
| --- | --- | --- |
| listen | `443 ssl http2` | `8080 ssl http2` |
| 프록시 대상 | 8091 / 8092 / 8093 | 8081 / 8082 / 8083 |
| HSTS | 적용 | **미적용** (max-age 1년이 다른 포트에까지 영향을 주므로 의도적으로 제외) |
| 로그 분리 | 기본 | `/var/log/nginx/dev_{access,error}.log` |
| `/uploads/` | 캐시 없음 | `expires 7d` |
| Basic 인증 | 없음 | 주석 상태 (`auth_basic`, `.htpasswd` 준비만 되어 있음) |

인증서는 **prod와 동일한 것을 재사용**한다. TLS 인증서는 도메인 단위이며 포트와 무관하다.

### 8.5 컨테이너 내부 Nginx (프론트엔드)

`frontend/nginx.conf` — `nginx:1.27-alpine` 이미지 안에서 SPA를 서빙한다.

```
server {
    listen80;
    root/usr/share/nginx/html;
    indexindex.html;
    charsetutf-8;

    location / {
        try_files$uri $uri/ /index.html;   # SPA: 새로고침 404 방지
    }
    gzipon;
    gzip_typestext/css application/javascript application/json;
}
```

`try_files ... /index.html` 는 React Router가 처리하는 `/chat` 같은 경로로 **새로고침** 했을 때 404가 나지 않도록 모든 미매칭 요청을 `index.html`로 넘기는 설정이다.

### 8.6 HTTPS 인증서

| 인증서 | 도메인 | 키 타입 | 인증 방식 | 만료일 |
| --- | --- | --- | --- | --- |
| `i15b208.p.ssafy.io` | `i15b208.p.ssafy.io` | ECDSA | **webroot** (2026-08-09 전환) | **2026-11-07** |
| `p.ssafy.io` | `*.p.ssafy.io` (와일드카드) | ECDSA | manual (SSAFY 관리, 팀 소관 아님) | 2026-09-21 |

#### 8.6.1 인증 방식: standalone → webroot 전환 (2026-08-09)

기존에는 `authenticator = standalone` 이었다. 이 방식은 Certbot이 갱신 시점에 **자체적으로 임시 웹서버를 띄워 80번 포트를 직접 점유**한다. 그런데 80번은 평소 Nginx가 리다이렉트용으로 쓰고 있으므로(8.3.1), 두 프로세스가 같은 포트를 다투다가 갱신이 실패했다.

**webroot 방식**으로 전환해, Certbot이 별도 서버를 띄우지 않고 이미 떠 있는 Nginx의 `/var/www/html`에 인증 파일만 놓도록 바꿨다. Nginx의 `/.well-known/acme-challenge/` location이 그 파일을 서빙한다.

```bash
sudo certbot certonly --webroot \
  -w /var/www/html \
  -d i15b208.p.ssafy.io \
  --cert-name i15b208.p.ssafy.io \
  --deploy-hook "systemctl reload nginx"
```

전환 후 `/etc/letsencrypt/renewal/i15b208.p.ssafy.io.conf`의 `authenticator` 값이 `webroot`로 바뀐다.

#### 8.6.2 상태 확인

```bash

sudo systemctl list-timers | grep certbot
sudo certbot renew --dry-run     # 실제 발급 없이 갱신 과정만 리허설
```

### 9.3 외부 접속 / 관리용 접속

DB와 Redis는 호스트 포트에 바인딩하지 않는다.
따라서 로컬 PC에서 일반적인 SSH 터널 방식인
`-L 3307:127.0.0.1:3306` 으로는 직접 접속할 수 없다.

표준 관리 방식은 서버에 SSH 접속한 뒤, 컨테이너 내부에서 직접 접속하는 것이다.

```bash

# prod DB 접속

# dev DB 접속

# prod Redis DB 0
docker exec -it emour-redis redis-cli -a '<REDIS_PASSWORD>' -n 0

# dev Redis DB 1
docker exec -it emour-redis redis-cli -a '<REDIS_PASSWORD>' -n 1
```

### 9.4 백업

`/opt/emour/scripts/backup.sh` — cron으로 **매일 04:00** 실행.

```bash
#!/bin/bash
set -e
BACKUP_DIR=/opt/emour/data/backup
DATE=$(date +%Y%m%d_%H%M%S)
mkdir -p "$BACKUP_DIR"

docker exec emour-db sh -c \
  'exec mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --databases emour --single-transaction' \
  | gzip > "$BACKUP_DIR/db_$DATE.sql.gz"

tar czf "$BACKUP_DIR/uploads_$DATE.tar.gz" -C /opt/emour/data uploads

find "$BACKUP_DIR" -name "*.gz" -mtime +14 -delete
echo "[$(date)] backup done"; df -h /
```

- `single-transaction`: 테이블 잠금 없이 일관된 스냅샷을 뜬다(서비스 중단 없음)
- 14일 지난 백업 자동 삭제
- **`emour_dev` 스키마는 백업 대상이 아니다** (운영 데이터만 보존)

복구:

```bash
gunzip -c /opt/emour/data/backup/db_20260809_040000.sql.gz \
  | docker exec -i emour-db mysql -uroot -p'<MYSQL_ROOT_PASSWORD>'
```

### 9.5 정리(cleanup)

`/opt/emour/scripts/cleanup.sh` — cron으로 **매주 일요일 05:00** 실행.

```bash
docker image prune -af --filter "until=168h"
docker builder prune -f --filter "until=168h"
docker container prune -f
sudo journalctl --vacuum-time=14d
```

CI가 배포마다 새 이미지를 만들기 때문에 디스크가 빠르게 찬다. 7일 지난 이미지·빌드 캐시를 주기적으로 회수한다.

## 10. 배포 시 특이사항

### 10.1 반드시 지켜야 할 사항

| # | 항목 | 내용 |
| --- | --- | --- |
| 1 | **컨테이너 포트는 `127.0.0.1`에 바인딩** | `"8092:8080"`처럼 쓰면 Docker가 iptables를 직접 조작해 **UFW 규칙을 우회**한다. 반드시 `"127.0.0.1:8092:8080"` 형식을 유지한다. |
| 2 | **기동 순서** | `data/docker-compose.db.yml` → `prod` / `dev`. `emour-net`을 DB compose가 만들고 나머지는 `external: true`로 참조하므로 순서를 어기면 네트워크 없음 오류가 난다. |
| 3 | **`VITE_*`는 빌드 인자** | 런타임 환경변수로 넣어도 반영되지 않는다. 값이 바뀌면 **이미지를 다시 빌드**해야 한다. |
| 4 | **Compose `${VAR}` 치환은 `.env`에서만** | `env_file:`로 지정한 파일은 컨테이너 내부 주입용이며, compose 파일 안의 `${VAR}` 치환에는 쓰이지 않는다. |
| 5 | **DDL 수동 적용** | 서버 프로파일에 `ddl-auto`가 없다. 엔티티가 바뀌면 `Emour_SQL_schema.sql`을 갱신하고 직접 적용해야 한다. |
| 6 | **`user: "1000:1000"`** | api 컨테이너가 호스트의 `ubuntu`(uid 1000)와 같은 uid로 실행되어야 `/opt/emour/data/uploads` 쓰기 권한 문제가 나지 않는다. |
| 7 | **AI 컨테이너 기동 시간** | Hugging Face 모델을 **런타임에 내려받아 메모리에 적재**한다. compose `start_period: 120s`, Dockerfile HEALTHCHECK `start-period=90s`. 첫 기동은 수 분 걸릴 수 있으므로 즉시 실패로 판단하지 않는다. |
| 8 | **AI 워커는 1개 고정** | `uvicorn --workers 1`. 워커를 늘리면 모델이 프로세스마다 중복 적재되어 메모리가 초과된다. |
| 9 | **SSAFY 서버 예약 포트** | `8988`, `8989`, `29418`은 이전 기수 Gerrit이 사용하던 포트다. **절대 사용·변경하지 않는다.** |
| 10 | **태그 교차 배포 차단** | `deploy.sh`가 `prod`에는 `master-*`, `dev`에는 `develop-*`만 허용한다. 수동 배포 시에도 태그 규칙을 지켜야 한다. |

### 10.2 알려진 제약 : `uploads` 디렉토리 dev / prod 공유 — 운영 편의상 보완 필요

- 두 환경 모두 `/opt/emour/data/uploads` 를 마운트한다.
- **검토 결과**: 저장 파일명이 `yyyy/MM/dd/{UUID32자리}.ext` 형식(`LocalFileStorage.java`)이라 **생성 및 삭제에 따른 문제 발생하지 않는다.** Nginx `autoindex`도 꺼져 있어 디렉토리 목록 노출도 없다.
- **실질적으로 남는 문제는 운영 편의 측면 하나뿐이다**: `backup.sh`가 `/opt/emour/data/uploads` 디렉토리 전체를 통째로 백업하므로, dev에서 올린 테스트 이미지가 prod 백업 용량에 함께 섞여 들어간다.
- **보완안**: 마운트 경로를 `/opt/emour/data/uploads/{prod,dev}` 로 분리하고 Nginx `alias`, `APP_UPLOAD_DIR` 매핑을 각각 수정. 급하지 않은 개선 과제로 분류.

### 10.3 트러블슈팅

| 증상 | 확인 |
| --- | --- |
| 배포 후 헬스체크 실패 | `docker compose logs --tail 100 <service>` |
| WebSocket 연결 실패 | `/etc/nginx/conf.d/websocket.conf` map 존재 확인, `WEBSOCKET_ALLOWED_ORIGIN_PATTERNS`에 접속 도메인 포함 여부 |
| AI 응답 지연/타임아웃 | `docker stats prod-ai` 메모리 확인. 모델 로딩 중이면 `/health`가 실패한다 |
| 이미지 업로드 실패(413) | Nginx `client_max_body_size 30m` 확인 |
| 새로고침 시 404 | 컨테이너 내부 `nginx.conf`의 `try_files` 확인 |
| 디스크 부족 | `df -h /` → `/opt/emour/scripts/cleanup.sh` 수동 실행 |
| DB 연결 실패 | `docker ps`로 `emour-db` healthy 확인, `emour-net` 소속 여부 확인 |
